# آزمون ۱۰هزار درخواست همزمان — ۲۴ مهر ۱۴۰۵

سرویس در این آزمون کرش نکرد، اما موج اتصال‌های جدید بدون خطا نبود. این نتیجه
تضمین ظرفیت ۱۰هزار کاربر یا آپلود همزمان فایل‌های بزرگ نیست.

## محیط و روش

- API با تنظیمات **Release** در پورت اختصاصی `5082`، بدون تغییر تنظیمات سرویس اصلی.
- دیتابیس آزمایشی جدا روی PostgreSQL 17 موجود؛ پس از بررسی داده‌ها حذف شد.
- ویندوز، ۱۰ هسته و ۱۶ پردازندهٔ منطقی، حدود ۱۶ گیگابایت رم؛ در شروع حدود
  ۳٫۴ گیگابایت رم آزاد بود. مولد بار، API و Docker روی همین دستگاه اجرا شدند.
- ۶۴ حساب مشتری و ۱۲۸ تیکت اولیه. تست ورود و ۱۰هزار اتصال SignalR جزو این آزمون نبود.
- HTTP/1.1، حداکثر ۱۰هزار اتصال در مولد بار، بدون تلاش مجدد؛ مهلت هر درخواست ۱۲۰ ثانیه.
- در هر موج اصلی، ۱۰هزار درخواست در فاصلهٔ ۱۶۵ تا ۲۶۵ میلی‌ثانیه ارسال شدند.
  تعداد درخواست‌های معلق در کلاینت به ۱۰هزار رسید. این عدد به معنی اجرای همزمان
  ۱۰هزار کوئری روی دیتابیس نیست؛ انتظار برای اتصال و منابع نیز در تأخیر حساب شده است.
- اتصال‌های HTTP بین موج‌ها دوباره استفاده شدند؛ بنابراین موج‌های نوشتن از
  اتصال‌های گرم استفاده کردند. خطاهای اتصال موج نخست دوباره ارسال نشدند.

۱۵۷ خطا از نوع `ECONNREFUSED` بودند؛ برای این اتصال‌ها پاسخ HTTP دریافت نشد.
از این اندازه‌گیری به‌تنهایی نمی‌توان علت دقیق رد اتصال را تعیین کرد. پاسخ HTTP
با کد ۵۰۰ و timeout در موج‌های اندازه‌گیری‌شده ثبت نشد.

## منابع و صحت ذخیره‌سازی

- بیشترین رم ثبت‌شدهٔ فرایند API: **۲۶۵۸ MiB، حدود ۲٫۶ GiB**.
- کمترین رم آزاد ثبت‌شدهٔ کل دستگاه: **۵۳۶ MiB**. نمونه‌برداری هر پنج ثانیه بود؛
  اوج واقعی بین نمونه‌ها ممکن است بیشتر باشد. شرط توقف محافظتی ۵۱۲ MiB فعال نشد.
- در پایان، سرویس به درخواست فهرست در **۶٫۹۳ میلی‌ثانیه** پاسخ موفق داد.
- تلاش برای ایجاد اتصال مدیریتی جدید به PostgreSQL پیش از توقف نمونهٔ تست، با
  `sorry, too many clients already` رد شد. تنظیم `max_connections` برابر **۱۰۰** بود.
  پس از توقف نمونهٔ تست، تعداد اتصال‌های PostgreSQL به **۶** کاهش یافت.
- بررسی مستقیم دیتابیس بعد از توقف API تست: **۲۰٬۱۲۸ تیکت، ۲۰٬۱۲۸ پیام و
  ۱۰٬۰۰۰ پیوست**؛ تمام پیوست‌ها ۶۵٬۵۳۶ بایت بودند. تعدادها با ۱۲۸ تیکت اولیه و
  ۲۰هزار ثبت موفق تطبیق داشتند. مجموع محتوای پیوست‌ها **۶۵۵٬۳۶۰٬۰۰۰ بایت** بود.
- سرویس اصلی و فرانت بعد از تست پاسخ HTTP ۲۰۰ دادند. داده‌های اصلی تغییر نکردند.

## حدود نتیجه

پیوست آزمایشی یک PNG کوچک با padding صفر تا ۶۴ KiB بود؛ محتوای آن بسیار
فشرده‌پذیر است. اندازهٔ نهایی دیتابیس فقط **۲۷ MB** شد، پس این آزمون هزینهٔ دیسک
و WAL مربوط به عکس‌ها و ویدئوهای فشرده‌ناپذیر را نمایندگی نمی‌کند. فایل‌های تا
۲۰ MiB، بار مداوم طولانی، چند سرور، شبکهٔ واقعی و مسیر پروکسی Next.js در این
آزمون اندازه‌گیری نشدند. آزمون خواندن ۱۰هزارتایی نیز پیش از ایجاد ۲۰هزار تیکت
انجام شد؛ خواندن بعد از ایجاد آن داده‌ها با همزمانی ۱۰۰۰ بررسی شد.

بنابراین نتیجهٔ قابل اتکا این است: نمونهٔ فعلی بار آزمایشی را بدون کرش پشت سر
گذاشت، اما فشار رم، اشغال ظرفیت اتصال دیتابیس و خطاهای موج اتصال جدید اجازهٔ
تضمین عملکرد بدون خطا در ۱۰هزار درخواست همزمان واقعی را نمی‌دهند.

مولد بار: [`scripts/load-test.mjs`](../scripts/load-test.mjs).
دادهٔ خام همین اجرا در `TestResults/load-test.json` و خروجی API در
`TestResults/load-api.log` نگهداری شد؛ این مسیر طبق `.gitignore` وارد گیت نمی‌شود.
برای اجرا، ابتدا دیتابیس مجزا و API Release روی `127.0.0.1:5082` بسازید؛ سپس:

```powershell
$env:TICKETING_LOAD_TEST_ISOLATED = '1'
node scripts/load-test.mjs http://127.0.0.1:5082 TestResults/load-test.json <test-api-process-id>
```

توکن‌ها و اطلاعات اتصال در گزارش ذخیره نمی‌شوند. پس از هر اجرا، فقط فرایند API
تست و دیتابیس مختص همان اجرا را پاک‌سازی کنید.
